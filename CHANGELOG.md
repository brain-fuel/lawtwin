# Changelog for `lawtwin`

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),

## Unreleased

### Added
- The repository, checked by canon 0.2.0 from its first commit: `canon.yaml`, the reference registry, the decision ledger with the owner's decisions of 2026-10-09 (`DEC-three-planes`, `DEC-twins-wire-level-containers`, `DEC-dependency-contracts-in-lawspec`, `DEC-twins-in-rust`, `DEC-fidelity`, `DEC-typed-control-plane`, `DEC-first-release-scope`, `DEC-vetting-deferred-to-1.0`), and exemptions that defer vetting to 1.0
- Documentation: the three planes, the roadmap, the Kafka contract's reference, how to run a contract's laws, and the LawSpec gap report
- The Kafka dependency contract, the LawSpec package `lawtwin.kafka` 0.1.0, under `contracts/kafka/`: the `Broker` ability with one operation per Kafka request and its stateful spec handler `reference`, the reference model of topics, partition logs, producer ids, epochs and sequences, transactions and their markers, groups, generations, assignments and committed offsets (`DEC-kafka-broker-and-clients`, `DEC-kafka-model-scope`); the client abilities `Admin`, `Producer`, `Partitioner`, `Consumer`, `GroupCoordinator` and `Transactions` with spec handlers written over `Broker`; and 39 laws, among them order within a partition, dense offsets, at-least-once delivery from committed offsets, idempotent retries written once, zombie producers fenced by a new epoch, read-committed isolation, every partition assigned once per generation, and stale generations refused
- `contracts/kafka/test/`, the project that runs the contract's laws on Rust, Python, Go, Java and Kotlin, with native handlers made with each case's `Cluster`, which holds the generated reference model (`DEC-contract-test-shared-cluster`)
- `lawtwin import openapi`, in a new Cargo workspace (`crates/lawtwin`): it reads an OpenAPI 3.0 or 3.1 document, in JSON or YAML, and writes a LawSpec dependency-contract package. Objects become records, enums sums, `oneOf` and `anyOf` sums of their alternatives, `allOf` merged records, arrays `List`, maps `KeyVal Text`, and nullable or optional values `Maybe`; bounds, lengths, patterns, formats and item counts become named refinements and `valid<Type>` definitions the model checks (`DEC-openapi-constraints-as-validation`). Each tag is an ability, each path and method an operation that fails with `ApiError`, a constructor per documented failing status. Resources (create, read, list, replace, update and delete by key, under parent paths) get a stateful reference model and laws: a created record reads back, a deleted one is not found, the list holds a created one, an update changes only the fields it gives, and a replaced one reads back (`DEC-openapi-resources`). What it cannot model goes to a hand-written unit, and hand-written laws to a laws unit, both written once. It also writes the test project, with native handlers on Rust and Python, and `lawtwin-openapi.json`, the wire map. `--tag` and `--path` select operations
- `contracts/petstore` (`lawtwin.petstore`), imported from the Swagger Petstore (OpenAPI 3.0), and `contracts/github` (`lawtwin.github`), imported from GitHub's label and milestone endpoints; both compile with `lawspec check` and their laws pass on Rust and Python. The documents are vendored in `openapi/` with their licences
- `make build`, `make test`, `make openapi-import` and `make openapi-import-check`; `make ci` runs the importer's tests and checks the imported contracts are current
- Documentation: the OpenAPI importer's reference, and how to import an OpenAPI document; the gap report lists five more LawSpec gaps the importer found
- `make lawspec-stage` and `tools/stage-lawspec.sh`, which stage the LawSpec CLI from a source checkout and run its native compiler, for LawSpec builds not yet on npm; `make lawspec-version` names the LawSpec the contracts need
- The Kafka contract's test project runs its laws on F# and C# too, with native handlers made with each case's `Cluster`, as on the other targets; the gap report lists one more gap, found there (33), now closed: all 79 runs pass on both
- The Kafka twin's Rust core, `twins/kafka/rust` (the program `lawtwin-kafka`): the Kafka contract's reference model, as LawSpec branch `lawspec-lawtwin` (e99a0bc) generates it, behind the Kafka wire protocol with the `kafka-protocol` crate (`DEC-embed-generated-model`). It answers ApiVersions, Metadata, Produce, Fetch, ListOffsets, FindCoordinator, JoinGroup, SyncGroup, Heartbeat, LeaveGroup, DescribeGroups, ListGroups, OffsetCommit, OffsetFetch, InitProducerId, AddPartitionsToTxn, AddOffsetsToTxn, TxnOffsetCommit, EndTxn, CreateTopics, CreatePartitions and DescribeConfigs at the versions librdkafka, the Java client, franz-go and kafkajs negotiate (`DEC-kafka-wire-versions`), each mapped onto the contract's `Broker` operations; v2 record batches with CRC32C in every compression; topic auto-creation; long polls; and the classic group protocol run over the contract's coordinator (`DEC-classic-groups-over-coordinator`). A build script binds the generated `cluster` handler so a refusal comes back as the contract's `KafkaError`
- The control plane, the same for every twin and every core (`DEC-control-plane-api`): an admin API described by `docs/reference/control-plane.openapi.yaml`, and the `lawtwin` commands `up`, `inspect`, `force`, `fault`, `faults`, `advance`, `history`, `replay`, `laws`, `seed` and `reset`. Forced states are reached through the contract's operations and an impossible one is refused with the law that forbids it (`DEC-force-through-operations`); faults are declared in the twin file `contracts/kafka/lawtwin.json`, beside the contract, with their effect on each law (`DEC-twin-file`): broker unavailable, leader change, consumer lag, duplicate delivery, rebalance storm and request latency; the twin clock is frozen unless advanced, and randomness is seeded (`DEC-twin-clock`); the history is the contract's ability calls with the model's answers, replayable through a fresh model and checked against the laws (`DEC-history-as-ability-calls`)
- The core conformance kit, `twins/kafka/conformance` and `make core-conformance CORE=<command or image:...>` (`DEC-core-conformance-kit`): librdkafka 2.12.1, kafkajs 2.2.4, franz-go 1.22.1 and the Java client 4.3.1 each produce and consume, rebalance a group, use the idempotent producer with a lost acknowledgement, run transactions read committed with a fenced zombie, see every fault, and read a forced state; the kit replays each history through the reference model and checks the laws over it; the same seed gives the same history byte for byte; and every core must answer the golden session in `twins/kafka/shared/golden` byte for byte. The Rust core passes it as a program and as an image. `make golden` records the session again
- A core per LawSpec target language (`DEC-core-per-target`, which supersedes `DEC-twins-in-rust`): the repository keeps a twin's cores side by side under `twins/<twin>/<language>/`, and everything else once
- The image `lawtwin/kafka:0.1.0` (also tagged `docker.io/lawtwin/kafka:0.1.0`, as Ironframe names it), 6 MB, from `twins/kafka/rust/Containerfile` with `make image`; the Rust core answers librdkafka at about two million records a second produced and half a million read; it takes `TWIN_CONFIG`, `LAWTWIN_SEED`, `LAWTWIN_CLOCK` and `LAWTWIN_ADVERTISE`. `examples/kafka/compose.yaml` runs it with podman compose
- Documentation: the control plane, the Kafka twin, Kafka twin cores, how to run the Kafka twin and drive it from a test, and how to check a core; the gap report lists five more gaps, found embedding the model and regenerating with the `lawspec-lawtwin` branch (28 to 32), and marks the ones that branch closes
- The HTTP twin's Rust core, `twins/http/rust` (the program `lawtwin-http`): any imported OpenAPI contract's reference model, as LawSpec generates it, behind HTTP/1.1. One core is a registry of every compiled contract and serves the one it is started with (`DEC-http-contract-registry`). Requests are routed and read by the wire map; one that breaks the document is refused with 400, or 422 where the operation documents it, and the document's failure body built from its schema (`DEC-http-refusals`); answers get the documented status, media type, JSON body, `Location` and required headers, and a `Date` from the twin clock; unmodelled operations answer 501. It serves the shared admin API: forced states reached through each resource's create, update and replace and refused with the law that forbids them, the history as the contract's calls, replay, the laws over the history and the state, the clock and the seed. `--mutant drop-field` and `--mutant skip-delete` make it part from its contract on purpose, for tests
- HTTP faults, declared in each contract's twin file `contracts/<name>/lawtwin.json` with their effect on each law: `latency`, `server-error`, `rate-limit` (429 with `Retry-After`, in windows of the twin clock), `timeout`, `connection-reset` and `slow-body`, each limited by operation, count, seeded probability or time, and answering before the model or, with `applied=true`, after it (`DEC-http-faults`)
- `lawtwin-wire` (`crates/lawtwin-wire`), the wire map read once for cores, peers and conformance runs: LawSpec types, values to and from JSON, requests read as calls and built from them, responses read as the model's answers, documented failure bodies, seeded valid and invalid traffic, the history format and the laws checked over a history or a state, and a small HTTP/1.1 client
- The OpenAPI client twin, `lawtwin peer http call --contract <name> --target <url>`: seeded traffic along the sequences the contract's laws are about, and on request broken requests, retries, duplicates and hang-ups; it checks the laws over the answers and reports violations, findings and problems (`DEC-openapi-client-twin`)
- `lawtwin record http`, a recording proxy that writes each exchange as a call of the contract, checked against the document; `lawtwin replay http`, which replays a trace through the twin and checks the trace against the contract; and `lawtwin conform http`, which runs the same traffic against a real service and the twin and grades it conformant, lawful or divergent. Answers are compared in the contract's terms (`DEC-http-replay-in-contract-terms`). Against a hand-written Petstore the trace replays with no divergence and both mutants are caught; the divergences of the Swagger Petstore 3 are in the ledger (`DEC-petstore3-divergences`)
- `lawtwin up http --contract <name>`, as a program or the image
- The HTTP core conformance kit, `twins/http/conformance` and `make core-conformance-http CORE=<command or image:...>`: golden sessions for the Petstore and GitHub contracts in `twins/http/shared/golden`, answered byte for byte; seeded sessions whose histories replay through the reference model and keep the laws; forced states; every fault as reqwest sees it; typed reqwest and curl clients, and a Python client generated from the Petstore's document by openapi-generator (`make openapi-client-http`). The Rust core passes it in process, as a program and as the image. `make golden-http` records the golden sessions again
- The image `lawtwin/http:0.1.0` (also `docker.io/lawtwin/http:0.1.0`), 4.7 MB, from `twins/http/rust/Containerfile` with `make image-http`, configured by `TWIN_CONFIG` (`contract`, `seed`, `clock`, `advertise`) or `LAWTWIN_CONTRACT`, `LAWTWIN_SEED`, `LAWTWIN_CLOCK` and `LAWTWIN_ADVERTISE`; `examples/http/compose.yaml` runs the Petstore and GitHub twins from it (`make compose-up-http`)
- `examples/http/petstore-app`, a Petstore written by hand with bugs to switch on, and `examples/http/petstore3/Containerfile`, which builds the Swagger Petstore 3 from source for the machine's architecture
- Documentation: the HTTP twin, HTTP twin cores, how to run the HTTP twin, test an application with the client twin, record and replay HTTP traffic and check conformance, and check an HTTP core

- `lawtwin record kafka`, a Kafka protocol proxy in front of a real broker (`DEC-recorded-history`): it decodes each exchange into the contract's history with the broker's answers, compares each answer with the reference model up to a renaming of the ids, epochs and generations the broker chooses (`DEC-compare-up-to-renaming`), checks the laws as it goes, and writes the trace as history and frames. It offers clients only what the twin answers (`DEC-recorder-negotiates-twin-versions`) and serves the control plane against the real broker: the declared faults applied on the wire, and forced topics, records and committed offsets reached by sending the broker the contract's operations (`DEC-recorder-control-plane`); retriable errors are notes, not answers (`DEC-retriable-errors-not-answers`)
- `lawtwin replay kafka <trace> --core <command | image:... | rust>`, which sends a trace's requests to a fresh core over the Kafka protocol in the order the recording allows, renaming ids as the core hands them out, and compares both sides' decoded answers (`DEC-replay-over-the-wire`, `DEC-fetch-sizing`). A session recorded from apache/kafka with librdkafka replays through the Rust core with no divergence, and a core built with the feature `mutant-ignore-dedupe`, which writes an idempotent retry again, is caught
- `lawtwin conform kafka --real <bootstrap>` and `make conform-kafka`, which starts `apache/kafka:4.3.1` in podman (`tools/real-kafka.sh`): the core conformance kit's 24 client scenarios run against the real broker through the recorder and against the twin, with the kit's law checks over each history, and the report gives a level per twin release (`DEC-conformance-levels`). Release 0.1.0 reaches level 3 against apache/kafka 4.3.1: every scenario passes and every law holds against it, and its divergences are ledger decisions (`DEC-kafka-divergence-group-assignment`, `DEC-kafka-divergence-rebalance-heartbeat`, `DEC-kafka-divergence-coordinator-timing`, `DEC-kafka-divergence-auto-create`, `DEC-fenced-producer-spelling`). The report and its traces are in `twins/kafka/conformance/reports/0.1.0/`, and the traces replay through the Rust core in a test that needs no broker
- `lawtwin peer kafka produce`, an external producer of records valid under the contract, with values generated from a seed and a LawSpec type and its refinements, at a rate, with keys, headers, idempotence, transactions and faults (duplicate, poison, tombstone, abort, late, hang); and `lawtwin peer kafka consume`, a group member that checks what it reads against the consumer-side laws and the value type, telling committed records from aborted ones by reading each partition both ways (`DEC-simulated-peers`, `DEC-peer-value-types`). Both work against the twin and real Kafka; `examples/kafka/orders.lawspec` is an example value type
- `twins/kafka/fidelity`, the program `lawtwin-kafka-fidelity` the commands above run; `make fidelity-test` runs its tests against apache/kafka in podman
- Documentation: references for recording, replay, conformance and the peers, and how to check conformance, record and replay Kafka traffic, and feed and check an application with the peers

### Changed
- The Rust core answers a fenced producer INVALID_PRODUCER_EPOCH on AddPartitionsToTxn, AddOffsetsToTxn and EndTxn below version 2, and on TxnOffsetCommit, as Kafka 4.3.1 does (`DEC-fenced-producer-spelling`); the history has a new source, `observed`, for state a recorded broker held before the recording
- The conformance kit's clients read a namespace from `LAWTWIN_NS` for their topics, groups and transactional ids, and the librdkafka scenarios are part of the kit's library, so they run against real Kafka too
- The wire map, `lawtwin-openapi.json`, now gives each field whether it is required, each parameter and field its constraints, each success response its documented headers, each failure its documented body, each resource its key type, parents, counter and laws by kind, and the model's `State`; the importer also writes the twin file `lawtwin.json` once. The Petstore and GitHub contracts are imported again; their LawSpec units do not change
- The control plane's OpenAPI document adds the HTTP twin's forced-state document and the fault parameter types `boolean`, `operation` and `status`; `make build`, `make test` and `make ci` cover the HTTP twin
- The contracts and the twin need LawSpec branch `integration-0.22` at f37e577, to be released as 0.23, staged with `make lawspec-stage`; every contract's test project is regenerated with it, and canon 0.2.2 checks the repository
- `make build` and `make test` cover the Rust core; `make ci` runs the core conformance kit
- The Kafka contract is re-expressed for LawSpec main after the `lawspec-gaps` merge, which closes 16 of the 17 gaps it found: one spec handler `cluster` answers `Broker`, `Admin` and `GroupCoordinator` by the model's checked definitions (`produceRequest by model.produce`), and the handler set `reference` adds the client handlers; operations `fail with KafkaError`; the model uses field access and record update, `prelude.range`, and saturating arithmetic; the facade unit is `lawtwin.kafka`; the murmur2 partitioner is written in the contract and checked against Kafka's vectors; every ability is declared `with Cluster`. `FetchedRecord`'s field `record` is now `entry`, which Java allows
- The Kafka test project binds no generators: LawSpec now generates topic names from the model's regex
- The gap report marks each closed gap, and lists five more found on the `lawspec-gaps` build
